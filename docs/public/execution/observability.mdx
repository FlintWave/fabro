Fabro captures a structured event for every significant action during a workflow run. These events cover stage execution, agent tool calls, retries, routing, sandbox lifecycle, git checkpoints, and more.

## Event stream

Every workflow run emits a sequence of canonical **run event envelopes** that are:

- Stored durably in the run store
- Broadcast over SSE to connected API clients
- Stored for later analysis
- Rendered by CLI progress and log tooling
- Optionally materialized into JSONL by export/debug paths

### Event names

Event names use lowercase dot notation, for example:

- `run.started`
- `step.started`
- `step.progress.recorded`
- `step.finished`
- `routing.resolved`
- `route.applied`
- `branch.completed`
- `run.stalled`

### Envelope format

Each serialized event envelope has a stable JSON shape:

```json
{
  "run_id": "01JQ...",
  "stream_seq": 42,
  "kind": "petri",
  "id": "execution 0/7/0",
  "recorded_at": 1795444788953,
  "item": {
    "id": {"log": "execution", "execution": 0, "seq": 7, "index": 0},
    "origin": "external",
    "subject": {"node": {"id": 2, "name": "verify"}, "firing": 2, "visit": 1, "attempt": 1},
    "record": {
      "seq": 7,
      "origin": "external",
      "recorded_at": 1795444788953,
      "body": {
        "event": "step.finished",
        "firing": 2,
        "attempt": 1,
        "outcome": {"status": "success", "output": {"outcome": "succeeded"}, "metrics": {"duration_ms": 5}}
      }
    }
  }
}
```

Envelope fields:

| Field | Description |
|---|---|
| `run_id` | Workflow run id |
| `stream_seq` | Durable per-run delivery sequence; the cursor used to resume |
| `kind` | `petri` for a Petri run event, `platform` for a stored Fabro platform record |
| `id` | The item's own identity, for deduplication |
| `recorded_at` | Milliseconds since the Unix epoch when the item's record was appended |
| `item` | The Petri `RunEvent` or stored platform record, unchanged |

The Petri event's name lives inside `item` (see `RunStreamItem::name`), typically at `item.record.body.event` or `item.derived.event`. Session, node, and other event-specific fields, formerly top-level, now live inside that nested `item` payload.

For runtime `for_each` branches, branch starts and completions are
`step.progress.recorded` records whose `ev.custom` payload has the kind
`attractor.parallel.branch.started` or `attractor.parallel.branch.completed`.
Those payloads include the zero-based `index` and an optional `item_label`.
They do not include the raw item. A prompt node's final prompt is recorded the
same way under `ev.custom` with the kind `attractor.prompt`, carrying the
rendered prompt text including any fenced item data, so event streams, run
dumps, and retained logs are source-bearing data. Apply the same
access controls and retention policy you use for workflow inputs.

## Reading the event stream

A record's event name sits at `.item.record.body.event`, with the event's fields beside it. View events (records with no stored line of their own, such as `branch.completed` and `run.stalled`) carry their name and fields under `.item.derived`.

```bash
# Count tool calls in a run (agent payloads ride in step.progress.recorded records)
fabro events 01JKXYZ... | jq -r 'select(.item.record.body.ev.custom.kind == "pebble") | .item.record.body.ev.custom.event.event | objects | .ToolCallStarted.tool_name // empty' | wc -l

# Find step failures
fabro events 01JKXYZ... | jq 'select(.item.record.body.event == "step.finished" and (.item.record.body.outcome.status | type == "object") and (.item.record.body.outcome.status | has("failure")))'

# See which edges were taken
fabro events 01JKXYZ... | jq 'select(.item.record.body.event == "route.applied" and .item.record.body.kind == "edge") | {from: .item.subject.node.name, to: .item.derived.target.name, back: .item.derived.back}'
```

If you need files on disk for offline analysis, `fabro dump` exports `events.jsonl` plus run-state projections.

## Event categories

Common categories include:

| Category | Example events |
|---|---|
| Run lifecycle | `run.started`, `execution.started`, `execution.finished`, `run.finished`, `run.paused`, `run.unpaused` |
| Stage (step) lifecycle | `step.started`, `step.finished`, `visit.started`, `visit.completed` |
| Step progress | `step.progress.recorded` records carrying log lines, artifacts, and structured step payloads |
| Agent activity | `step.progress.recorded` with `ev.custom.kind` of `pebble`; stage views name the pebble payloads `agent.message`, `agent.tool.started`, `agent.warning`, `agent.sub.spawned` |
| Agent todo state | pebble todo payloads inside `step.progress.recorded`; stage views name them `todo.created`, `todo.updated`, `todo.deleted` |
| Routing | `routing.resolved`, `route.applied` |
| Git and checkpoints | `checkpoint` (platform record), `run.diff` (platform record) |
| Platform records | `run.created`, `run.lifecycle`, `run.notice`, `artifact.collected`, plus other `PlatformRecordKind` values |

The canonical post-response payload for an agent turn is pebble's `AssistantMessage` event, forwarded in a `step.progress.recorded` record under `ev.custom`. When context-window data is available, it appears on the message payload as `context_window`; there is no separate context-window snapshot event to consume.

## Sub-agent visibility

Sub-agent activity now appears as pebble payloads on the same `step.progress.recorded` records as the parent's agent events, with the pebble envelope carrying the session linkage:

- `session_id` identifies the session that produced the event
- `parent_session_id` identifies its immediate parent on a child session's events

Lifecycle payloads such as `SubAgentSpawned` and `SubAgentCompleted` are published by the parent session, and stage views name them `agent.sub.spawned` and `agent.sub.completed`. Tool calls and other child activity are forwarded with their original `session_id`.

## Real-time monitoring

### API: Server-Sent Events

When running workflows through the API server, subscribe to the [run events endpoint](/api-reference/runs/stream-run-events). Each SSE payload is a serialized run event envelope in the same shape used by `fabro events` and `events.jsonl` exports.

### Web UI

The web frontend consumes the SSE stream automatically and shows stage progress, tool calls, command output, and human interaction as they happen. Use the stage `Chat` view for a readable conversation, `Thread` for the detailed agent transcript and disclosed provider reasoning, and `Debug` for raw stage events. Use the run-level `Run Events` page when you need the full event stream with search and category filters. The `Run Events` page also includes a Waterfall view for comparing stage durations and inspecting timing details from hover popovers.

### CLI progress

The CLI renders live progress from the same envelope format. This is written to stderr so stdout remains pipe-friendly.

## Post-run analysis

Post-run analysis surfaces include:

| Surface | Description |
|---|---|
| `fabro events <RUN>` | Full event envelope stream as NDJSON |
| `fabro logs <RUN>` | Raw per-run worker tracing log, when available |
| `fabro inspect <RUN>` | Current durable run state, including run/start/checkpoint/conclusion records |
| `fabro dump --output <DIR> <RUN>` | Exported `events.jsonl` plus reconstructed JSON and node files |

See [stages](/api-reference/run-internals/list-run-stages) and [turns](/api-reference/run-internals/list-stage-turns) for higher-level analysis views built on top of this event stream.
